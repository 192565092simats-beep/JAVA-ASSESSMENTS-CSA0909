## 1. Problem Context: The "Too Many Open Files" OS Error
In Unix/Linux/macOS, every operating system process has a soft limit on the maximum number of concurrent open file descriptors (typically `1024` or `4096`). In an enterprise sales pipeline processing hundreds of store ledger files, if files fail to close due to unexpected parse errors, the OS table fills up rapidly until throwing:
```
java.io.IOException: Too many open files
```

## 3. Student B – Design & Correctness

### A. Why Manual `finally` Blocks Leak Resources
```java
// Flawed Manual Closing
finally {
    if (reader1 != null) reader1.close(); // If this throws IOException...
    if (reader2 != null) reader2.close(); // ... THIS LINE NEVER RUNS! (LEAK)
    if (writer != null) writer.close();   // ... AND THIS NEVER RUNS! (LEAK)
}
```
If any individual `.close()` method encounters an I/O error or flush failure and throws an exception, the thread unwinds immediately, skipping all remaining `.close()` invocations.

### B. How `try-with-resources` (TWR) Solves This
1. **Implicit Compilation**: Any object implementing `java.lang.AutoCloseable` declared within `try (...)` is guaranteed to be closed by compiler-generated bytecode.
2. **Reverse Order of Closure**: Resources are closed in **strictly reverse order of their declaration** (LIFO stack order):
   $$\text{Declaration: } R_1 \rightarrow R_2 \rightarrow R_3 \implies \text{Closing: } R_3.\text{close}() \rightarrow R_2.\text{close}() \rightarrow R_1.\text{close}()$$
3. **Suppressed Exceptions (`e.getSuppressed()`)**:
   - In manual `finally`, if both the `try` block and the `close()` method throw exceptions, the `close()` exception completely **overwrites and masks** the real business error.
   - In TWR, the primary exception from the `try` block is preserved. Any subsequent exceptions thrown during `.close()` are attached to the primary exception via `Throwable.addSuppressed()` and retrieved via `e.getSuppressed()`.

## 4. Joint Engineering Decision

### Under what conditions is `try-with-resources` NOT sufficient on its own?
1. **Non-`AutoCloseable` Legacy Interfaces**: Third-party C/C++ native libraries (JNI) or older APIs that use custom cleanup methods like `dispose()`, `release()`, or `destroy()` without implementing `AutoCloseable`.
2. **Asynchronous / Cross-Thread Hand-offs**: If a file, channel, or database connection is opened in thread $A$ but passed to a background worker thread $B$, closing it at the end of thread $A$'s lexical scope would destroy the resource prematurely.
3. **Atomic File Rollback**: TWR closes files upon failure, but it does **not delete partially written, corrupted output files**. A robust enterprise system requires an explicit rollback/compensating transaction (e.g. `Files.deleteIfExists(tempFile)`) to avoid corrupt downstream reports.

---

## 5. Alternative Concept & Complexity Analysis

### Comparison of Resource Management Strategies ($f$ Store Files)

| Strategy | Processing Time Complexity | Max File Handles Open on Failure | Risk of Masked Exceptions |
| :--- | :--- | :--- | :--- |
| **No Closing** | $O(f)$ | **$f + 1$ handles leaked** (Reaches OS descriptor ceiling) | High (Data corruption) |
| **Manual `finally` Close** | $O(f)$ | Up to $f$ handles leaked if a prior `close()` throws | **High**: Close error hides root failure |
| **`try-with-resources`** | $O(f)$ | **$0$ handles open** (Deterministic guaranteed cleanup) | **Zero**: Uses `getSuppressed()` |
